# MoreImg 提示词数据流契约

本文固定 MoreImg Web 应用当前的提示词数据流和职责边界，避免把“AI 生成视觉语义”和“前端拼合执行提示词”混为一谈。修改 `moreimg-1.0`、Style Lock、图片提示词或 HTML 卡片前，应先核对本文及 `prompt-pipeline-contract.test.mjs`。

## 一句话结论

文本 AI 负责理解文章并生成页面语义、Style Lock 和逐页视觉语义；前端不重新理解语义，只把已经生成的字段确定性拼合为图片 API 的执行提示词。HTML 只负责准确文字排版和有限的卡片外壳，不会把自然语言 Style Lock 自动转换成完整 CSS 风格。

## 当前数据流

```text
原文 + 加工偏好 + DEFAULT_SYSTEM_PROMPT
  -> 文本 AI（一次请求）
  -> moreimg-1.0 JSON
     - article：精修正文
     - pages[].card：HTML 可见文字
     - pages[].semantic：内容语义映射
     - style_lock：全套视觉 DNA
     - pages[].image_prompt：AI 生成的逐页视觉语义
  -> buildPageImagePrompt（前端字符串拼合，不做语义推理）
  -> 图片 API 执行提示词
  -> 无字主视觉
  -> HTML 叠加准确文字并导出 3:4 成品
```

## 字段职责

### `pages[].semantic`：内容语义源

由文本 AI 生成，记录页面目标、核心观点、主概念、主关系、辅助概念、排除概念和避免误读。

它用于说明“这一页真正表达什么”。当前前端会校验并展示这些字段，但 `buildPageImagePrompt` 不会直接读取 `semantic`。系统指令要求 `image_prompt.relationship` 与 `semantic.primary_relation` 一致，目前主要依赖文本 AI 遵守，前端尚未做语义等价校验。

### `style_lock`：AI 生成的全局视觉约束

由同一次文本 AI 请求生成，包含：

- `card_shell`：HTML 能执行的有限外壳参数。
- `prompt_prefix`：前端会直接拼入图片执行提示词的风格短语。
- `visual_dna`：媒介、视觉世界、造型、透视、光影、材质和重复主体等全局视觉语义。
- `negative`：全局负面约束。

当前 `buildPageImagePrompt` 直接使用 `prompt_prefix` 和 `negative`，不会逐项展开 `visual_dna`。`visual_dna` 的落实主要依赖 AI 同时把它反映在 `prompt_prefix` 和各页 `image_prompt.continuity` 中。

### `pages[].image_prompt`：AI 生成的逐页视觉语义

由文本 AI 根据页面语义和 Style Lock 生成，包括场景、主关系、构图、文字安全区、系列连续性和本页避免项。

它不是前端从 `semantic` 自动推导的结果，也不是普通 CSS 配置。`scene`、`composition` 和 `continuity` 可能已经包含当前 Style Lock 的人物、物体、视觉世界和构图方式。

### `buildPageImagePrompt`：执行提示词拼合器

该函数只做确定性字符串拼合：

```text
style_lock.prompt_prefix
+ image_prompt.scene
+ image_prompt.relationship
+ image_prompt.composition
+ image_prompt.safe_area
+ image_prompt.continuity
+ style_lock.negative
+ image_prompt.avoid
+ 固定无文字约束
```

它不调用 AI，不读取原文，不理解 `semantic`，也不会判断新旧风格是否冲突。因此应称为“图片执行提示词拼合器”，不能称为“语义提示词生成器”。

### HTML 卡片：文字与有限外壳

HTML 卡片读取 `pages[].card` 作为可见文字，并只把以下 `style_lock.card_shell` 字段映射为页面样式：

- `surface`
- `accent_color`
- `overlay`
- 固定的 `moreimg-clean-v1` preset

HTML 不会执行 `prompt_prefix`、`visual_dna`、`scene`、`relationship`、`composition` 或 `continuity`。杂志风、手绘风、3D 材质等完整视觉表现由图片 AI 执行，不会自动变成 HTML/CSS。

## 两条图片路径

### `moreimg-1.0` JSON 路径

JSON 包经过 `packagePageToPromptSection -> buildPageImagePrompt` 得到执行提示词。页面直接把该提示词传给“生成主视觉”；不会再次调用 `buildVisualOnlyPrompt` 做语义提取。

### 旧版阶段文本兼容路径

旧版阶段5文本会先由解析器拆分，再经过 `buildVisualOnlyPrompt` 删除文字和旧排版描述。这是兼容旧历史的清洗逻辑，不代表当前 JSON 路径会在前端重新生成视觉语义。

## 风格切换边界

当前没有独立的风格选择或后期风格适配流程。直接替换一个已完成 JSON 包中的 `style_lock`，最多会改变：

- HTML 的基础明暗、强调色和遮罩。
- 拼合提示词中的 `prompt_prefix` 与全局负面约束。

它不会重写已有 `image_prompt.scene`、`composition` 和 `continuity`。这些字段可能已经融入旧 Style Lock，因此不能把直接替换称为“完整换风格”。

可靠的完整换风格只有两条路线：

1. 在文本处理前选择 Style Lock，让同一次文本 AI 请求生成与它一致的逐页视觉语义。
2. 重新设计协议，把 AI 输出改为严格风格无关的视觉语义，再由结构化本地风格模板确定性编译执行提示词。

在完成第二条路线前，后期完整换风格需要重新调用文本 AI 生成 `style_lock` 和 `pages[].image_prompt`；生成新图片仍需要调用图片 AI。

## 不变量

后续修改必须保持或明确升级以下契约：

1. `semantic` 是内容语义映射，`image_prompt` 是 AI 生成的逐页视觉语义，二者不能混称为前端拼合结果。
2. `buildPageImagePrompt` 只负责拼合执行提示词，不得悄悄承担不可测试的自然语言推理。
3. JSON 路径不得误走旧版 `buildVisualOnlyPrompt` 清洗逻辑，否则可能删掉 AI 已生成的有效视觉语义。
4. HTML 只使用 `card` 和 `style_lock.card_shell`；若未来让 HTML 执行完整风格，必须新增明确的结构化 HTML 模板协议，不能直接解释自然语言 Style Lock。
5. 后期替换 Style Lock 不等于完成风格适配。若 UI 增加“换风格”，必须明确它是重新调用文本 AI，还是基于新协议重新编译。

## 修改检查清单

改动以下任一位置时，运行全部测试并重点检查 `prompt-pipeline-contract.test.mjs`：

- `DEFAULT_SYSTEM_PROMPT`
- `validateMoreImgPackage`
- `buildPageImagePrompt`
- `packagePageToPromptSection`
- `buildVisualOnlyPrompt`
- `getCardShellPresentation`
- JSON 路径与旧版路径的分支判断
